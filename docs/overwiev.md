# Техническое задание
## Clever Vibe — сервис фиксации результатов применения ИИ-ассистентов

**Версия 2.** Учтён дизайн-хендофф и принятые по нему решения.

**Дизайн-документация** лежит в репозитории в `docs/design/`:

| Файл | Что содержит |
|---|---|
| `docs/design/README.md` | Полное описание всех экранов, компонентов, поведения и состояний |
| `docs/design/prototype/Clever Vibe.dc.html` | Кликабельный прототип, открывается в браузере как есть |
| `docs/design/prototype/support.js` | Служебный рантайм прототипа |
| `docs/design/tokens/themes.css` | Токены трёх тем — переносится в проект |
| `docs/design/tokens/nocturne-styles.css` | Исходный токен-шит дизайн-системы Nocturne |
| `docs/design/tokens/nocturne-readme.md` | Гайд Nocturne: цвет, типографика, состояния, иконки |

Прототип — **дизайн-референс, а не продакшн-код**: он показывает задуманный вид и поведение, но написан инлайновыми стилями поверх CSS-переменных. Задача — воспроизвести экраны на Vue 3 + PrimeVue + Tailwind собственными компонентами, а `themes.css` превратить в тему.

**При расхождении прототипа и этого ТЗ приоритет у ТЗ** — ниже зафиксированы решения, принятые уже после хендоффа.

**Контекст:** пилот по внедрению ИИ-ассистентов во Frontend-разработке. Команда — 1 Team Lead + 3 разработчика, Angular-проект. Длительность — до 3 месяцев.

**Назначение:** накапливать факты применения ИИ-инструментов по ходу работы и давать сводную картину, какие подходы дают эффект, а какие нет.

**Не назначение:** сервис не оценивает разработчиков. Персональные срезы существуют только для того, чтобы человек мог подготовить свою сводку к ежемесячной встрече. В общекомандных представлениях авторство записей не раскрывается.

---

## 1. Ключевая сущность

**Одна запись = одно применение подхода.**

Не «задача», а именно применение. На одной задаче может быть 3 записи: сгенерировал компонент, потом сгенерировал тесты, потом прогнал свой PR через ИИ.

Ожидаемый объём за пилот: 300–600 записей.

## 2. Модель данных

### 2.1 User

| Поле | Тип | Примечание |
|---|---|---|
| id | uuid | |
| name | string | |
| login | string, unique | генерируется системой: транслит имени, при коллизии суффикс 2, 3, … |
| password | string | генерируется системой, 8 символов, алфавит без похожих знаков (0/O, 1/l/I) |
| role | enum | `dev` / `lead` / `admin` / `observer` |
| createdById | uuid | кто создал участника |
| active | bool | |

**Хеширование паролей не применяется — решение принято осознанно.** Пароль хранится в открытом виде и постоянно доступен лиду в админке, что заменяет собой механизм сброса. Обоснование: 4 участника, внутренний контур, пароль генерируется системой и нигде больше не используется. Следствие: сервис не должен принимать пароли, придуманные пользователями, и не должен иметь формы смены пароля — только перегенерацию лидом.

### 2.1.1 Роли и права

Четыре роли. Иерархии наследования нет — права заданы явно матрицей.

| Действие | dev | lead | admin | observer |
|---|---|---|---|---|
| Вносить записи | ✔ | ✔ | ✔ | — |
| Мои записи + сводка за месяц | ✔ | ✔ | ✔ | — |
| Дашборд | ✔ | ✔ | ✔ | ✔ |
| Экспорт CSV | — | ✔ | ✔ | ✔ |
| Справочник подходов: добавление, деактивация | — | ✔ | ✔ | — |
| Промоут кастомных подходов | — | ✔ | ✔ | — |
| Создание участников с ролью `dev` | — | ✔ | ✔ | — |
| Создание участников с ролью `lead`, `admin`, `observer` | — | — | ✔ | — |
| Деактивация участников | — | только `dev` | все | — |
| Просмотр и копирование паролей участников | — | только созданных им | все | — |

Пояснения:
- **admin** — техническая роль, заводит лидов и наблюдателей. В пилоте это, скорее всего, один человек, возможно вне команды.
- **lead** — заводит разработчиков в своей команде и ведёт справочник подходов: разбирает предложения из «другого подхода» и добавляет прижившиеся в справочник.
- **observer** — роль для менеджера направления или PM: видит дашборд и может выгрузить CSV, но не вносит записи и не имеет экрана «Мои записи». Пункт меню «Быстрый ввод» для него не отображается.
- Лид видит пароли только тех участников, которых создал сам; админ — всех.

### 2.2 Stage (справочник стадий)

Фиксированный справочник, сидируется при развёртывании.

| code | Название |
|---|---|
| `analysis` | Анализ задачи |
| `design` | Проектирование |
| `code` | Написание кода |
| `refactor` | Рефакторинг |
| `debug` | Дебаг |
| `test` | Тесты |
| `review` | Код-ревью |
| `docs` | Документация |
| `misc` | Прочее |

Поля: `code`, `title`, `order`, `active`.

### 2.3 Approach (справочник подходов)

Каждый подход привязан к одной стадии. Стартовый набор:

**analysis**
- Разбор требований (уточняющие вопросы, edge-кейсы, что не учтено)
- Декомпозиция задачи на подзадачи
- Генерация плана реализации до написания кода

**design**
- Обсуждение архитектурных вариантов
- Генерация структуры модуля / контракта API / типов
- Ревью собственного архитектурного решения

**code**
- Автокомплит в IDE
- Генерация по описанию задачи
- Чат-итерации (сгенерировал → поправь → уточнил)
- Агентный режим (правки в нескольких файлах)
- Генерация по образцу существующего компонента
- Миграция синтаксиса между версиями Angular
- Бойлерплейт (конфиги, скаффолдинг, типы, моки)

**refactor**
- Разбиение большого компонента / функции
- Устранение дублирования
- Модернизация легаси
- Оптимизация (перф, бандл)

**debug**
- Стектрейс + контекст → гипотезы причины
- Объяснение незнакомого / легаси-кода
- Генерация минимального репро
- Проговаривание проблемы в диалоге
- Анализ диффа («после этих изменений сломалось — где?»)

**test**
- Генерация unit-тестов по готовому коду
- Список сценариев / edge-кейсов, затем код тестов
- Дописывание покрытия по отчёту coverage
- Генерация тестовых данных, фикстур, моков
- Тесты по требованиям до написания кода
- E2E-сценарии по описанию юзер-флоу

**review**
- Само-ревью своего PR до отправки
- Второе мнение по чужому PR
- Проверка на соответствие конвенциям проекта
- Объяснение чужого PR перед ревью

**docs**
- JSDoc / комментарии по коду
- README / гайд по модулю
- Описание PR
- Changelog из коммитов
- Актуализация устаревшей документации

**misc**
- Коммит-месседжи
- Разбор ошибок сборки
- Регэкспы, SQL, конфиги
- Смысловой поиск по кодбазе

Поля: `code`, `stageId`, `title`, `description`, `order`, `active`, `isCustom`.

**Требование:** свободный ввод названия подхода запрещён — иначе через месяц в базе будут «генерация тестов», «ген. тестов» и «тесты через ИИ», и никакой агрегации не выйдет. Вместо этого есть вариант «другой подход» со свободным текстом в отдельное поле; лид раз в месяц просматривает такие записи и при повторяемости добавляет подход в справочник (`isCustom = true`).

### 2.4 Entry (запись о применении)

| Поле | Тип | Обяз. | Примечание |
|---|---|---|---|
| id | uuid | ✔ | |
| userId | uuid | ✔ | |
| createdAt | timestamp | ✔ | автоматически |
| stageId | uuid | ✔ | |
| approachId | uuid | ✔ | либо `customApproachText` |
| customApproachText | string | | если выбран «другой подход» |
| taskRef | string | | ключ задачи в трекере |
| tool | enum | ✔ | справочник инструментов |
| usefulness | int 1–5 | ✔ | польза |
| trust | int 1–5 | ✔ | доверие к результату |
| note | text | | свободная заметка |
| deletedAt | timestamp | | физического удаления нет |

**Шкала usefulness (польза):**
1. Помешало, потратил время впустую
2. Пользы почти не было
3. Немного помогло
4. Заметно ускорило
5. Сэкономило часы

**Шкала trust (доверие к результату):**
1. Выкинул полностью
2. Переписал большую часть
3. Существенно дорабатывал
4. Мелкие правки
5. Взял как есть

Шкала намеренно пятибалльная, а не 1–100: при сотне делений люди не различают соседние значения и группируются на круглых числах, диапазон схлопывается. Точность даёт не шкала, а количество записей.

### 2.5 Tool (справочник инструментов)

`code`, `title`, `active`. Заполняется списком утверждённых компанией инструментов при развёртывании.

### 3.1 Вход

- Логин + пароль, выданные лидом.
- При успешном входе связка сохраняется в localStorage; при последующих заходах — автовход без формы.
- Кнопка «Выйти» очищает сохранённую связку.
- Ошибки: «Неверный логин или пароль», «Участник деактивирован».
- Деактивированный участник не проходит и по автовходу.

### 3.2 Быстрый ввод — главный экран

**Раскладка A (Панель)** — единственная реализуемая. Варианты B (Поток) и C (Три колонки) из прототипа не делаем; в `docs/design/README.md` они описаны в том же разделе — игнорировать.

Грид `minmax(0,1fr) 336px`: слева форма, справа блок «Последние 3 записи» и легенда шкал.

**Требования:**
- Всё на одном экране, без переходов и скролла
- Цель по времени заполнения — 20–30 секунд
- Стадия и подход — чипсы; подходы фильтруются по выбранной стадии; последний чип «Другой подход» открывает поле свободного текста
- Инструмент — селект, запоминает последний выбор пользователя
- Оценки — два ряда по 5 кнопок с подписью текущего значения
- `taskRef` — опционально, tabular-nums
- Заметка свёрнута по умолчанию
- Кнопка активна только при выбранных подходе, пользе и доверии (для «другого подхода» — ещё непустой текст)
- После сохранения форма очищается, **стадия и инструмент сохраняются**
- Черновик пишется в `localStorage['aiTrackerDraft']` при каждом изменении, восстанавливается при загрузке, удаляется после сохранения

**Мобильная версия не делается.** Сервис только для десктопа.

### 3.3 Мои записи

- Грид `minmax(0,1fr) 400px`. Слева список с фильтрами (стадия, месяц / весь пилот) и счётчиком показанных.
- Строка записи: дата, подход + мета (стадия · инструмент · задача) + заметка, оценки, действия.
- «Изменить» / «Удалить» доступны 7 дней, дальше — «7 дней прошло». Удаление проставляет `deletedAt`.
- **Блок «Моя сводка за месяц»:** группировка стадия → подход → N, средняя польза, среднее доверие, свои заметки. При N < 5 строка приглушена и помечена «мало данных».
- Кнопка «Копировать текстом» кладёт сводку в буфер плоским текстом.

### 3.4 Дашборд

**Виджет 1 — квадранты «частота × польза».**
Каждый подход — точка. X = число применений командой, Y = средняя польза, размер = число записей, цвет = среднее доверие (< 2.6 → `--bad`, < 3.6 → `--warn`, иначе `--color-accent`).

Границы квадрантов — медианы по подходам, имеющим хотя бы одну запись.

**Пока в системе меньше 50 записей всего, границы квадрантов и подписи квадрантов не отображаются** — выводится только облако точек. Причина: на малых данных медиана смещается от каждой новой записи, и точки перескакивают между квадрантами, что читается как сломанный дашборд. При 50 и более записях границы появляются с подписью «границы предварительные».

Клик по точке → правая панель со всеми записями по подходу и заметками. **Автор записи не отображается.**

**Виджет 2 — покрытие стадий.** Стадия, полоса, «N n». Стадии с N < 5 подсвечиваются `--warn` с иконкой предупреждения.

**Виджет 3 — динамика средней пользы.** По месяцам, суммарно или по выбранной стадии. Значения при N < 5 приглушены.

**Виджет 4 — разброс между участниками.** По подходу — отрезок min–max средних оценок участников на шкале 1–5, справа «±дельта»; при разбросе ≥ 2 отрезок жёлтый.

**При N ≤ 5 по подходу отрезок не строится, вместо него выводится текст «недостаточно данных для формирования результата».**

**Виджет 5 — таблица подходов.** Подход, стадия, N, польза, доверие, охват (`n/4`), флаг «мало данных». Сортировка кликом по колонке, заголовок sticky, тело со скроллом. Клик по строке → та же панель записей.

**Общее правило:** рядом со средней всегда показывается N; при N < 5 значение приглушается и помечается «мало данных».

### 3.5 Администрирование (`lead` и `admin`)

Для ролей `dev` и `observer` пункт меню не отображается; при прямом обращении к маршруту — плашка «экран недоступен для вашей роли».

- **Кастомные подходы на разбор:** текст, **автор**, частота, период, кнопка «Промоутить» (после — «В справочнике», `isCustom = true`). Авторство здесь показывается: это рабочий инструмент для ведения справочника, а не оценка людей.
- **Справочник подходов:** фильтр по стадии, «+ Подход», строка с названием (+ бейдж `isCustom`), стадией, N, кнопкой «Деактивировать» / «Включить».
- **Пользователи:** «+ Пользователь» → имя + роль → «Создать». Система генерирует логин и пароль.
  - Список ролей в форме зависит от роли создающего: лид видит только `dev`, админ — все четыре.
  - **Пароль отображается постоянно, в списке участников, с кнопкой копирования** — это заменяет процедуру сброса. Лид видит пароли только созданных им участников, админ — всех.
  - Там же активация / деактивация и перегенерация пароля, в тех же границах видимости.
  - Лид не может деактивировать участника с ролью `lead`, `admin` или `observer`.
- **Экспорт CSV:** `id,userId,createdAt,stage,approach,customApproachText,taskRef,tool,usefulness,trust,note`. Для роли `observer` кнопка экспорта выносится на дашборд, поскольку экран администрирования ему недоступен.

**Открытый вопрос:** первый админ создаётся сидом при развёртывании (логин и пароль задаются переменными окружения). Кто и как заводит последующих админов — если такая потребность вообще есть при четырёх участниках — не определено; по умолчанию админ может создать другого админа.

### 3.6 Темы

Три темы: `nocturne` (по умолчанию), `black`, `mint`. Переключение атрибутом `data-theme` на корне.

Выбранная тема сохраняется в `localStorage['aiTrackerTheme']` **для пользователя** и подхватывается сразу при загрузке, до первого рендера — без вспышки чужой темы.

## 4. Расчёты

- Средняя польза подхода = среднее `usefulness` по всем его записям; среднее доверие = среднее `trust`
- Частота = count записей; охват = count distinct `userId`
- Медианы для границ квадрантов — по текущему набору подходов, имеющих хотя бы 1 запись
- Записи с `deletedAt` в агрегаты не входят
- Все выводимые числа округляются до одного знака после запятой

## 5. Нефункциональные требования

**Стек:** Fastify + Prisma + PostgreSQL, Vue 3 + PrimeVue + Tailwind.

**Иконки:** PrimeIcons. Phosphor, которым размечен прототип (список — в `docs/design/README.md`, раздел **Assets**), не используем — набор из PrimeVue закрывает потребность и не тянет лишнюю зависимость. Соответствия: `ph-x` → `pi-times`, `ph-plus` → `pi-plus`, `ph-minus` → `pi-minus`, `ph-warning` → `pi-exclamation-triangle`, `ph-arrow-up/down` → `pi-arrow-up/down`, `ph-download-simple` → `pi-download`, `ph-copy` → `pi-copy`, `ph-palette` → `pi-palette`, `ph-sign-out` → `pi-sign-out`.

**Шрифт:** Inter. Класть локально, не с CDN, если сервис едет во внутренний контур.

**Токены:** `docs/design/tokens/themes.css` переносится в тему PrimeVue (preset) / Tailwind theme, а не остаётся инлайновыми стилями. Правила построения шкал (перцептивная светлота, инверсия в светлой теме, роль `accent-2` для шкалы доверия) — в `docs/design/README.md`, раздел **Themes**, и в `docs/design/tokens/nocturne-readme.md`.

Таблица ролей токенов (что каким шагом красится: фон, поверхности, границы, текст, приглушённые значения) — в `docs/design/README.md`, раздел **Design Tokens**. Отклоняться от неё не нужно, она уже согласована с прототипом.

**Авторизация:** логин + пароль из БД, сравнение в открытом виде, сохранение связки в localStorage, автовход. Сессий и JWT не требуется. Роль возвращается вместе с профилем при входе; проверка прав обязательна и на бэкенде, а не только скрытием пунктов меню.

**Развёртывание:** бэкенд и фронт — Northflank (бесплатный Developer-план, 2 сервиса, 1 vCPU, 1 ГБ RAM, 0.5 ГБ постоянного тома, карта не требуется). БД — Neon (free).

Ключевая причина выбора: инстанс не засыпает, холодного старта нет. Обычный Node-процесс, Fastify без переделок, деплой из GitHub.

Отклонённые варианты:
- **Vercel** — Hobby-план запрещает коммерческое использование, а под определение коммерческого попадает в том числе проект, код которого пишет оплачиваемый сотрудник. Внутренний инструмент компании под это подпадает.
- **Render** — бесплатный веб-сервис засыпает после 15 минут простоя и поднимается около минуты. Для формы, куда заходят пару раз в день, это означает минуту ожидания почти при каждом заходе.

Оговорка по Northflank: в документации сказано, что бесплатный тариф не предназначен для продакшена. Это рекомендация, а не лицензионный запрет, но при бессрочном использовании после пилота стоит держать в уме.

Подключение к Neon: две строки в окружении — `DATABASE_URL` (pooled, через встроенный pgBouncer, для рантайма) и `DIRECT_URL` (прямое соединение, для миграций). В `schema.prisma` соответственно `url` и `directUrl`. Миграции — `prisma migrate deploy` в билд-шаге, не автоматом при старте приложения.

Два сервиса Northflank распределяются как бэкенд + фронт. Свободных сервисов не остаётся, поэтому отдельный воркер или крон в архитектуру не закладываем.

Репозиторий на GitHub — **приватный**.

**Экспорт:** CSV со всеми полями записей — обязателен, нужен для итогового отчёта.

**Адаптивность:** не требуется, только десктоп.

## 6. Вне скоупа

- Интеграция с трекером задач (`taskRef` хранится строкой, без связи)
- Автоматический сбор Velocity / Cycle Time / Defect Rate — ведутся отдельно, на стороне PM
- Мобильная версия
- Раскладки быстрого ввода B и C
- Уведомления и напоминания
- Смена пароля пользователем
- Роли сверх четырёх: `dev`, `lead`, `admin`, `observer`
- Смена ролей у существующего участника (при необходимости — пересоздание)
- Мультипроектность
